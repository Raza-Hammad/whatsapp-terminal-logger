# Taste — Command Code
- Explicitly separates analysis from action: when asking for a project or file to be read/understood, expects zero edits ("do not do anything in the project") and just a notification when finished. Treat read-only as the default until changes are requested. Confidence: 0.75
- Values thorough, accurate coverage over sampling — expects the whole project *and* every sheet/section of source data files to be read end to end before any summary or conclusion. Confidence: 0.6
- Prefers concise confirmation when a task is complete, plus a short high-level recap rather than an unfocused dump. Confidence: 0.45
- Writes prescriptive fix specs (enumerated root causes, exact file paths, numbered steps, and code snippets) and expects them implemented as written — including the specific fallback ordering and named properties. Confidence: 0.6
- Expects a bug fixed at every affected layer end to end (extension, server, dashboard) rather than patched at a single point. Confidence: 0.6
- Expects broad coverage of a feature area rather than only the named case — if files/attachments are in scope, all document and media types must be handled, not just the ones listed in the request. Confidence: 0.5
- Values explicit, greppable diagnostic logging (prefixed tags plus per-item outcome messages) as part of a fix. Confidence: 0.4
- Reports bugs as loosely-phrased user-visible symptoms, often with "also check overall …" appended, and expects root-cause diagnosis plus a fix that sweeps the whole related feature area (every media type, multi-attachment bursts), not just the exact reported instance. Confidence: 0.7
- Judges AI reply quality by whether replies are actually grounded in the attachment content (voice notes, images) — generic "conversation flow" answers are treated as broken behavior to be fixed, not acceptable fallback. Confidence: 0.6
- Debugs by pasting raw, unedited log output (browser console or the app's terminal/server logs, full stack traces and third-party noise included) as the entire bug report, with a one-line symptom such as "still not getting VMs" or "its not working accurately"; expects the agent to isolate the decisive line and trace it to root cause instead of asking for a curated summary. Confidence: 0.55
- Treats "logged but not actually delivered" as a broken feature: everything the engine reports as generated must reach the real recipient, and silently skipping/dropping queued output (e.g. dropping a second reply bubble to stay inside a latency budget) is unacceptable — better to send all parts, even slightly late, and log a per-item sent/failed result. Confidence: 0.62
- Judges a fix by whether the feature works in the live running app — stubbed/unit-test passes do not count, and the same symptom recurring after a "validated" fix is treated as the fix being incomplete. Confidence: 0.55
- Wants domain/brand facts grounded in authoritative external sources — explicitly asks the agent to search and visit the official website before answering about a company or product, rather than relying on assumed knowledge. Confidence: 0.6
- Prefers hard scope boundaries in behavior design: out-of-scope input should produce no response at all (empty output / stay silent) rather than a polite deflection or small talk. Confidence: 0.45
- Later revised the above: once marketed as a human agent, out-of-scope questions should get a short, casual steer-back to the supported topic instead of total silence — the current stated preference is "always say something human, but only answer in-domain." Confidence: 0.5
- Strongly rejects anything that reads as a chatbot: bot replies must sound like a real named human ("John"), casual and short on WhatsApp, never "As an AI…" / "I'm here to assist…" phrasing, and should match the contact's language and script (Roman Urdu vs English). Confidence: 0.7
- Language matching is driven by the *newest* incoming DM, not the conversation history: a DM in English, Roman Urdu, Urdu script, etc. should be answered in exactly that language/script, and an explicit request in the DM ("reply in English", "Urdu mein jawab do") overrides everything. Confidence: 0.75
- Wants address style to adapt to the contact's formality level: respected/formal contacts ("Sir", honorifics, aap-pronouns) get "sir" instead of the casual "yaar", in generated replies as well as in canned fallback/steer-back lines. Confidence: 0.6
- Prefers short, terse human-sounding canned lines (e.g. "Ek sec yaar, batata hoon." over "Ek sec yaar, dekh ke batata hoon.") and expects exact copy strings to be reproduced verbatim when specified. Confidence: 0.45
- Latency budgets for interactive features are targets for engineering work (trimming fallback chains, capping model output, local text extraction), but they are *not* allowed to degrade the answer — see the accuracy-first learning below. Confidence: 0.5
- Correct, real replies outrank speed: when a short generation deadline caused canned fallback lines to be sent over and over, he pushed back with "our main goal is not just to bound response time… responding to DM perfectly and accurately is the main goal" and expects the deadline widened into a pure safety net (per-attempt timeout → next key/model → fallback only when every API key is exhausted/rate-limited), never a cutoff that aborts healthy requests. Confidence: 0.7
- Treats a repeated identical canned reply ("getting the same messages again and again") as a top-severity bug, not a cosmetic one — repetition itself is the signal that the fallback path is firing when it shouldn't. Confidence: 0.6
- States feature changes as desired end behavior and constraints ("lower the constraint that it gossips", "should not sound like AI", "within 10 secs") and leaves the implementation strategy to the agent, in contrast to prescriptive root-cause specs for bug fixes. Confidence: 0.5
- Uses terse nudges ("continue", or re-pasting a failed request verbatim after an infra/auth error) and expects the agent to resume the in-flight task without re-asking for context or re-explaining the plan. Confidence: 0.5
